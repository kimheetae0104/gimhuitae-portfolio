01 — 문제 정의

결과물은 나온다. "내가 원하는 톤"은 안 나온다.

ChatGPT도 이제 캐러셀 카드뉴스를 만든다. 하지만 폰트·여백·강조·흐름이 일관되게 잡힌 "발행 가능한 결과"를 받으려면 결국 디자인 지식이 필요하다.

Problem 01

결과의 일관성이 들쭉날쭉

같은 주제라도 매번 톤·구성이 달라진다. 만족스러운 결과가 나올 때까지 다시 돌리거나, 손으로 다듬어야 한다.

Problem 02

일관성을 잡으려면 디자인 지식 필요

폰트 크기 · 강조 키워드 · 줄바꿈 · 카드 간 흐름. 결국 디자인을 아는 사람만 "발행 가능한" 결과까지 끌어올린다.

INKK의 가설

일반 사용자가 막히는 지점은 "AI가 못 만들어서"가 아니라 일관성을 잡는 디자인 기술이 없어서다. 그 기술을 서비스 안에 내장하면, 누가 써도 발행 가능한 결과가 처음부터 나온다.

02 — 제품 결정

발행 속도를 판다. 고민할 거리부터 제거.

경쟁 상대는 캔바가 아니라 "오늘 그냥 안 올리는 선택"이다. 그래서 예쁜 편집 자유도 대신 발행 속도에 모든 결정을 걸었다.

01
입력은 주제 한 줄. 길이에 따라 카드 수(5–10장)를 자동 추천해 사용자가 고민할 지점을 없앴다.
02
디자인은 선택이 아니라 프리셋. 색·타이포·여백이 한 세트로 묶인 검증된 스타일 6종 — 무드만 고른다.
03
첫 장은 훅 패턴으로 별도 강제. 통계·숫자·권위·질문 등 훅 패턴을 프롬프트 변수로 빼, 커버 카피를 의도적으로 세게 만든다.
04
Before/After로 가치를 즉시 증명. "같은 주제·같은 시간"을 밋밋한 슬라이드 vs INKK 카드로 나란히 보여준다.

03 — 기술 딥다이브 · 품질 엔진

품질을 운에 맡기지 않는 4층 방어.

AI 카드뉴스의 흔한 실패는 '틀린 결과'가 아니라 '맞지만 밋밋한 결과'다. 문법은 멀쩡한데 아무도 저장하지 않는 카드. 그래서 품질을 4개 층에서 강제했다.

01

장별 역할 분리 프롬프트

"카드뉴스 만들어줘"는 평행 슬라이드를 만든다. 장마다 다른 지시를 받게 갈랐다 — 커버는 스크롤을 멈추는 훅, 본문은 핵심 사실 1문장 + 수치, 마지막은 저장·공유 유도. 장마다 다른 역할을 받으면 기승전결 흐름이 생긴다.

02

GOOD / BAD 반례로 '밋밋함' 차단

LLM은 "좋은 카피를 써라"보다 구체적 반례에 훨씬 잘 반응한다. 흔히 나오는 밋밋한 패턴을 프롬프트에 미리 박아 차단하고, 강한 카피 패턴은 예시로 제시한다.

03

휴리스틱 품질 점수 — 통과 못 하면 자동 재생성

LLM 출력을 그대로 믿지 않고 점수 기반 평가를 통과해야 사용자에게 나간다. 통과 못 하면 사유와 함께 다시 돌린다.

  • 형식 검증 · 헤딩·본문 길이 범위, 추상 키워드 사용 감점
  • 언어 오염 방어 · 일본어·한자 누출 감점 (한국어 LLM 응답 안정성)
  • 임팩트 검증 · 본문에 수치 부재, 마지막 카드 CTA 누락 감점
04

레이아웃 엔진 — LLM 출력 길이 편차를 자동 흡수

텍스트 길이를 측정해 폰트 크기·행간·레이아웃 타입을 자동 매핑한다. 글이 짧든 길든 카드 비율이 항상 균형 잡힌다.

  • 레이아웃 자동 선택 · 풀블리드 / 상하 2중 / 좌우 2중 / 4중 그리드 / 오버레이 캡션 — 텍스트 비율에 맞춰 자동 결정 (위 deck 참고)
  • 이미지 슬롯 보정 · LLM이 이미지 수를 틀려도 자동으로 채우거나 잘라 정규화
  • 출력 정제 · 길이 초과·과한 강조(느낌표 등)는 후처리에서 일괄 정리
핵심 철학

퀄리티는 "좋은 프롬프트 한 방"이 아니라 여러 층의 강제 장치가 누적된 결과다. 프롬프트가 80%를 잡고, 점수·sanitize·레이아웃이 나머지 20%의 들쭉날쭉함을 메운다.

04 — 아키텍처 · 보안

돈이 걸린 서비스, 동시성·멱등성부터.

크레딧이 곧 현금이라, 기능보다 "동시 요청·재시도에도 잔액이 안 깨지는가"가 먼저였다. 보안 감사 라운드에서 권한 회수 결함까지 찾아 정리했다.

잔액

크레딧 차감을 DB 안에서 원자 처리

잔액이 곧 현금이라, 동시 요청이 들어와도 음수가 되지 않도록 차감 자체를 DB 트랜잭션 안에서 처리한다. 클라이언트는 잔액에 직접 접근하지 않는다.

  • 행 잠금 차감 · 잔액을 잠근 뒤 확인·차감, 동시 요청에도 잔액이 음수로 깨지지 않음
  • 권한 분리 · 모든 잔액 변경은 서버 측 함수만 수행, 클라이언트 직접 업데이트 불가
  • 실패 시 자동 환불 · LLM 호출이 실패하면 잔액을 자동 복구 (총 구매 이력은 보존)
결제

Stripe 웹훅 — 같은 이벤트가 여러 번 와도 한 번만

Stripe는 at-least-once 전송이라 같은 결제 이벤트가 여러 번 들어온다. 이벤트 처리 상태를 별도 테이블에 기록해 한 번만 적립되도록 강제한다.

  • 중복 처리 방어 · 이미 처리된 이벤트는 즉시 무시
  • 재시도 복구 · 처리 도중 크래시가 나도 일정 시간 후 자동 재시도 가능 (영원히 잠긴 row 방지)
  • 상태 머신 · 모든 경로(성공·실패·예외)에서 처리 상태가 명확히 마킹
보안

변경 API · 이미지 프록시 · DB 권한 다층 방어

결제·잔액·LLM 비용이 걸린 서비스라 보안 기본기를 다층으로 깔았다. 한 군데 뚫려도 다음 단계에서 막히도록.

  • 변경 API · 출처 검증으로 외부 사이트의 위변조 요청 차단
  • 이미지 프록시 · 허용된 호스트만 통과, 내부망 IP·메타데이터 대역 접근 차단
  • DB 권한 · 행 단위 격리(RLS) + 민감 함수는 서버 전용으로 권한 회수
  • 감사 라운드 · 출시 전 권한 결함을 자체 감사로 발견·회수 (베타 진입 시 노출 0건)

05 — 출시 이후 · 운영

고치기 전에 측정한다.

제품이 도는 것과 사업이 되는 것은 다르다. 출시 후엔 기능을 더 쌓는 대신 "왜 안 쓰는지 보이게" 만드는 일에 집중했다.

기능보다 측정을 먼저

코드를 더 쌓기 전에 퍼널 이벤트 로깅과 관리자 대시보드를 먼저 깔았다. 측정 없는 최적화는 다음 달에 또 감으로 결정하게 만든다.

무료 깔때기 재설계

초기 무료 횟수가 가치를 느끼기도 전에 결제 벽에 부딪혔다. 무료 한도를 늘리고, 결제가 막는 지점을 '생성 횟수'가 아니라 '발행 가능 상태'로 옮겼다 — 습관이 먼저, 결제는 그다음.

병목은 코드가 아니라 인프라 위치

"느리다"를 감으로 추측하지 않고 측정부터. 원인은 DB가 아니라 서버리스 함수의 지역 설정이었고, 설정 한 줄 변경으로 API 응답이 수 배 빨라졌다. 비싼 마이그레이션 전에 가설을 데이터로 교정한 사례.

안 만들기로 한 결정

'카드 1장만 재생성' 기능은 원가가 새 덱과 비슷했고 수동 편집이 이미 그 needs를 커버해 만들지 않기로 했다. 남은 진짜 병목은 코드가 아니라 유입.
