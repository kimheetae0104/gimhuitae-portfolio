01 — 문제

결과물은 나온다. "내가 원하는 톤"은 안 나온다.

ChatGPT도 이제 캐러셀 카드뉴스를 만든다. 하지만 폰트·여백·강조·흐름이 일관되게 잡힌 "발행 가능한 결과"를 받으려면 결국 디자인 지식이 필요하다.

PROBLEM 01

결과의 일관성이 들쭉날쭉

같은 주제라도 매번 톤·구성이 달라진다. 만족스러운 결과가 나올 때까지 다시 돌리거나, 손으로 다듬어야 한다.

PROBLEM 02

일관성을 잡으려면 디자인 지식 필요

폰트 크기·강조 키워드·줄바꿈·카드 간 흐름 — 결국 디자인을 아는 사람만 "발행 가능한" 결과까지 끌어올린다.

INKK의 가설

일반 사용자가 막히는 지점은 "AI가 못 만들어서"가 아니라 일관성을 잡는 디자인 기술이 없어서다. 그 기술을 서비스 안에 내장하면, 누가 써도 발행 가능한 결과가 처음부터 나온다.

02 — 제품 결정

속도가 핵심. 고민할 거리 제거

경쟁 상대는 캔바가 아니라 '오늘 그냥 안 올리는 선택'이다. 그래서 예쁜 편집 자유도 대신 발행 속도에 모든 결정을 걸었다.

01
입력은 주제 한 줄. 길이에 따라 카드 수(5~10장)를 자동 추천해 사용자가 고민할 지점을 없앴다.
02
디자인은 선택이 아니라 프리셋. 색·타이포·여백이 한 세트로 묶인 검증된 스타일 6종 — 무드만 고른다.
03
첫 장은 훅으로 별도 패턴화. 통계·숫자·권위·질문 등 훅 패턴을 변수로 빼, 커버 카피를 의도적으로 세게 만든다.
04
Before/After로 가치를 즉시 증명. "같은 주제·같은 시간"을 밋밋한 슬라이드 vs INKK 카드로 나란히 보여준다.

03 — 기술 딥다이브 · 품질 엔진

'AI 티'는 프롬프트 한 방으로 안 지워짐

AI 카드뉴스의 흔한 실패는 '틀린 결과'가 아니라 '맞지만 밋밋한 결과'다. 문법은 멀쩡한데 아무도 저장하지 않는 카드. 그래서 품질을 운에 맡기지 않고 4개 층에서 강제했다.

01

카드마다 '역할'을 분리한 프롬프트

"카드뉴스 만들어줘"라고 하면 모든 장이 비슷한 톤의 평행 슬라이드가 된다. 그래서 장별 역할을 프롬프트에서 명시적으로 갈랐다 — 커버는 스크롤을 멈추는 훅, 본문은 핵심 사실 1문장 + 수치, 마지막은 저장·공유 유도. 장마다 다른 지시를 받으니 기승전결 흐름이 생긴다.

02

GOOD / BAD 반례로 '밋밋함'을 차단

LLM은 "좋은 카피를 써라" 같은 추상 지시보다 구체적인 반례를 줄 때 훨씬 잘 따른다. 밋밋한 출력 패턴을 프롬프트에 박아 미리 차단했다.

BAD: "시장에서의 위치를 확인할 수 있습니다." ← 공허함 BAD: ["전문가 의견 참고", "시장 위치 파악"] ← 공허함 GOOD: "원장이 **숨기는** 1가지"
03

구조적 제약 — 길이·강조·줄바꿈까지 규칙화

  • heading 20자 이하·단정형 — 모바일에서 안 잘리고 강하게
  • heading마다 강조 키워드 1개 필수 — 시선이 멈출 지점 보장
  • 느낌표는 카드 전체 합쳐 최대 1번 — 싸 보이는 과장 톤 억제
  • 줄바꿈 균형 — 마지막 줄에 "1가지"만 덩그러니 남지 않게 어절 배분
04

레이아웃 엔진 + 후처리 — LLM 출력은 불신

layout-engine이 텍스트 길이를 측정해 폰트(30자 48px → 120자 22px)·레이아웃 타입·행간을 자동 조정해, 글이 길든 짧든 카드가 항상 균형 잡힌다. 마지막으로 sanitize가 heading을 45자로 하드 트렁케이트하고, 규칙 어긴 느낌표를 마침표로 일괄 치환하며 정제한다.

핵심 철학

퀄리티는 "좋은 프롬프트 한 방"이 아니라 여러 층의 강제 장치가 누적된 결과다. 프롬프트가 80%를 잡고, 구조·레이아웃·후처리가 나머지 20%의 들쭉날쭉함을 메운다.

04 — 아키텍처 · 보안

돈이 걸린 서비스, 동시성·멱등성부터

크레딧이 곧 현금이라, 기능보다 "동시 요청·재시도에도 잔액이 안 깨지는가"가 먼저였다. 보안 감사를 4라운드 반복해 webhook 멱등성·CSRF·SSRF·크레딧 정합성을 검증했다.

DB
크레딧 차감을 RPC로 원자화. deduct_credit을 SELECT FOR UPDATE 트랜잭션으로 — 동시 요청에도 잔액이 음수로 안 깨진다.
결제
Stripe webhook 멱등 처리. at-least-once 전송이라, claim_stripe_event RPC로 중복·재시도 이벤트가 크레딧을 두 번 적립하지 못하게.
보안
RLS + 이미지 SSRF 가드. 전 테이블 행 단위 격리, 외부 이미지는 호스트 화이트리스트·DNS 검증 후 중계.
유연성
LLM 프로바이더 추상화. Groq(빠름·저렴) 기본, Claude(고품질)로 런타임 전환 — 비용/품질 레버를 코드에 고정하지 않음.
Next.js 16 · RSC Supabase · Postgres · RLS Stripe · 크레딧 충전 Groq · Claude Upstash · Rate limit Vitest · CSRF 테스트

05 — 출시 이후 · 운영

고치기 전에 측정

제품이 도는 것과 사업이 되는 것은 다르다. 출시 후엔 기능을 더 쌓는 대신 "왜 안 쓰는지 보이게" 만드는 일에 집중했다.

측정을 먼저

최적화보다 퍼널 이벤트 로깅·관리자 대시보드를 먼저 깔았다. 측정 없는 최적화는 다음 달에 또 감으로 결정하게 만든다.

무료 깔때기 재설계

초기 "평생 2회"는 가치를 느끼기도 전에 결제 벽에 부딪혔다. 7일 체험 + 월 5회 무료로 바꾸고, 결제가 막는 걸 '생성 횟수'가 아니라 '발행 가능 상태(워터마크)'로 옮겼다 — 습관이 먼저, 결제는 그다음.

성능 ~6배

"느리다"를 측정부터. 원인은 DB 지역이 아니라 Vercel 함수가 미국이라 태평양을 왕복한 것. regions:["icn1"] 한 줄로 API 0.4s → 0.06s. 비싼 마이그레이션 전에 가설을 데이터로 교정했다.

안 만들기로 한 결정

카드 1장 재생성 기능은 원가가 새 덱과 비슷했고 수동 편집이 이미 그 니즈를 커버해 만들지 않기로 했다. 남은 진짜 병목은 코드가 아니라 유입이다.
