02 · WHY LOCAL AI STARTING POINT

AI를 쓰고 있었지만,
내가 통제하고 있진 않았다.

AI를 개발 도구로 쓰기 시작하면서 가장 먼저 부딪힌 건 비용보다 작업 흐름이 자주 끊기는 문제였다. 프롬프트가 길어지고 컨텍스트가 쌓일수록, 어느 순간 작업을 이어가기 어려워졌다.

클라우드 AI를 쓸 때는 컨텍스트 길이, 비용, 연결 상태에 따라 작업 흐름이 자주 끊겼다.

그 답답함이 출발점이었다. 비용을 줄이려는 것보다, AI를 도구처럼 호출하는 방식과 내 환경 안에 붙여 쓰는 방식이 어떻게 다른지 확인해보고 싶었다.

토큰 걱정 없이, 인터넷 없이, 내 컴퓨터에서 끝까지 이어지는 워크플로우가 가능한지 궁금했다.

동기에서 호기심으로
01
컨텍스트 한도 초과
긴 작업 도중 강제 세션 초기화. 흐름이 끊긴다.
02
월 비용 불안정
사용량에 따라 청구액 변동. 예산을 통제할 수 없다.
03
데이터 외부 전송
모든 프롬프트가 외부 서버로 — 민감 데이터에 부담.
→
로컬 AI = 소유 가능한 인프라
제어할 수 있고 끊기지 않고 외부에 의존하지 않는 워크플로우. 그 가능성이 궁금해서 시작했다.

03 · LEARNING PATH FOLLOW · BUILD · EXTEND
출발점 · Connect AI Lab

따라 만든 다음 내 방식으로 다시 붙였다.

Connect AI Lab EP.3를 출발점으로 삼았다. 하지만 그대로 재현하는 데서 멈추지 않고, 같은 환경을 직접 구성하고 도구를 바꿔가며 왜 이 조합이 필요한지 살펴봤다.

"왜 이 도구가 여기에 들어가는가?" 영상이 답하지 않은 질문을 스스로 묻고, 직접 바꿔보면서 기준을 정리했다.

Fig. REF — Connect AI Lab · EP.3

5단계로 본 학습 흐름
01
환경 구성
macOS에 Ollama를 설치하고 `llama3.2`, `gemma`, `qwen`을 직접 띄웠다. 4-bit 양자화 모델이 실제 환경에서 돌아가는지부터 확인했다.
→ 양자화·VRAM 사용량의 trade-off를 처음 체감.
02
Obsidian Vault 연결
개인 노트 디렉토리를 컨텍스트 소스로 연결했다. Vault 구조와 백링크가 검색 품질에 어떤 차이를 만드는지 확인했다.
→ 좋은 노트 구조 = 좋은 컨텍스트 = 좋은 응답.
03
AntiGravity 파이프라인 결합
Obsidian → Ollama → 출력 → 다시 Vault로 이어지는 흐름을 AntiGravity로 묶었다. 단발 호출이 아니라 루프형 워크플로우를 만들었다.
→ "모델 호출"이 아닌 "파이프라인 설계"라는 관점 획득.
04
모델별 라우팅 실험
텍스트 분석은 Gemma, 일반 추론은 Llama 3.2, 코드는 Qwen2.5-Coder로 나눠 같은 입력에서 결과를 비교했다.
→ "큰 모델 1개"보다 "작은 모델 여럿 + 라우팅"이 더 효율적인 경우 확인.
05
IDE 안으로 끌어오기 (확장)
VS Code에 Connect AI 익스텐션을 붙여 편집기 안에서 로컬 모델과 직접 대화했다. 코드 컨텍스트와 노트 컨텍스트를 한 흐름으로 묶어봤다.
→ 영상에 없던 다음 단계를 스스로 시도한 지점.

04 · STACK 5 TOOLS · WHY THIS COMBO

도구를 많이 쓴 게 아니라 역할을 나눠 붙였다.

5개를 한꺼번에 붙인 게 아니라, 각 도구가 다른 층을 맡도록 설계했다. 어느 하나가 빠져도 루프가 끊긴다.

KNOWLEDGE LAYER
Obsidian
마크다운 기반 개인 지식 그래프. 백링크·태그로 노트가 자동 연결되며 Vault 전체가 컨텍스트 소스가 된다.
→ Vault 구조 자체가 컨텍스트 큐레이션이다. 잘 정리된 노트 = 좋은 응답.
800+ 노트 · 작업별 폴더 분리 · 모델 입력 토큰 자동 집계
INFERENCE LAYER
Ollama
로컬 LLM 실행 엔진. Llama·Gemma·Qwen·Mistral 등 양자화 모델을 단일 CLI로 다운로드·실행·교체.
→ "모델 호출"을 추상화. 모델 교체가 하루치 작업이 아닌 한 줄 수정.
6개 모델 동시 관리 · 4-bit 양자화 기본 · GPT4ALL에서 갈아탐
ORCHESTRATION
AntiGravity
AI 워크플로우 오케스트레이션 허브. 입력→처리→출력 루프와 작업별 모델 라우팅을 한 워크플로우로 묶는다.
→ 이 한 칸이 빠지면 그냥 챗봇. 단발 호출을 자동 루프로 만드는 핵심.
분류 → 라우팅 → Vault 기록 자동 트리거
GLUE LAYER
Python
통합 구현 언어. Ollama API 호출, 파일 I/O, Vault 변경 감지 자동 기록까지 전부 Python으로 처리.
→ 각 층을 잇는 접착제. 자유도 최고, AI 코드 생성과 궁합이 좋다.
requests · watchdog · pyyaml · Vault 변경 → 자동 처리
PAIR PROGRAMMING
Claude
설계·코드 리뷰·디버깅 페어. AI로 AI 시스템을 만드는 메타 루프 — 로컬 모델로는 부족한 추론을 보완.
→ 로컬 AI를 만드는 동안 클라우드 AI에게 검토받는 게 가장 빠른 학습.
아키텍처 결정 · CSS 디버깅 · 이 포트폴리오 구성까지

05 · ARCHITECTURE 3-STAGE LOOP

노트에서 꺼내고, 로컬에서 처리한 뒤 다시 노트로 보냈다.

세 단계가 닫힌 루프를 만든다. 노트에서 컨텍스트를 꺼내 로컬 LLM이 처리하고, 결과를 다시 Vault에 기록하면서 지식 그래프가 스스로 자란다.

외부 API 호출 0건 · 데이터 로컬 유지 · 토큰 한도 없음.

$ ollama run llama3.2 --context vault/notes/
✓ Model loaded (3.2B params, 4-bit quantized)
✓ Vault scanned: 12 notes, 4,200 tokens
✓ Response generated in 2.1s (local GPU)
✓ Output saved → vault/output/summary_240428.md
# 외부 API 호출 0건, 비용 $0, 데이터 로컬 유지
STAGE 1 · INPUT

Obsidian Vault

마크다운 노트에서 컨텍스트 추출. 백링크·태그를 따라 관련 문서를 자동 수집한다.
.md · 링크 · 태그
STAGE 2 · PROCESS

Ollama + AntiGravity

작업 유형(분석·요약·코드)을 AntiGravity가 분류해 적합한 로컬 모델로 자동 라우팅.
gemma · llama3.2 · qwen-coder
STAGE 3 · OUTPUT

Vault 자동 기록

생성된 요약·분석·태그를 다시 Obsidian으로. 지식 그래프가 유기적으로 성장.
summary.md · backlinks

06 · EXPERIMENTS TRIED · TESTED · DROPPED

추천 스택보다 직접 바꿔보며 세운 기준이 더 중요했다.

"이게 좋다"는 말을 그대로 믿지 않고 같은 입력으로 직접 비교했다. 실제로는 처음에 잡은 스택 중 그대로 남은 게 거의 없었다. 교체하고 제거하는 과정에서 기준이 더 분명해졌다.

EXPERIMENT 01 · 모델 비교
3개 모델, 같은 작업으로 직접 돌리기
무엇을: Llama 3.2 (3.2B) · Gemma 4 E4B (4B) · Qwen2.5-Coder (7B)
어떻게: 같은 입력 3종으로 응답 품질과 속도를 직접 비교.
결과: 텍스트 분석은 Gemma, 코드는 Qwen, 일반 추론은 Llama가 더 잘 맞았다. 단일 모델로 전부 처리하는 방식은 비효율적이라는 걸 확인했다.
→ "큰 모델 1개"보다 "작은 모델 여럿 + 라우팅".
EXPERIMENT 02 · 양자화
같은 모델을 4-bit / 8-bit로 비교
무엇을: Llama 3.2 동일 모델, 양자화 수준만 변경.
어떻게: 동일 입력으로 응답 시간·메모리·품질 차이를 비교.
결과: 4-bit가 더 빠르고 메모리도 적게 썼다. 일반 Q&A는 차이가 작았지만, 코드 작업에선 8-bit가 더 안정적이었다.
→ 양자화 수준도 작업 유형별로 다르게.
EXPERIMENT 03 · 시행착오
썼다 뺀 것들
GPT4ALL → Ollama: 모델 관리·CLI 통합 한계.
13B → 3-4B 양자화: 응답 시간이 비실용적이라 다운사이즈.
직접 짠 프롬프트 체인 → AntiGravity: 분기·상태 관리 복잡.
결과: 처음 정답처럼 보이던 도구들이 대부분 교체됐다. 비교·교체·제거 자체가 학습 과정의 본체였다.
→ 빼본 것이 가장 큰 배움이었다.

08 · WHAT'S NEXT OPEN QUESTIONS
이 실험을 통해 모델 성능보다 워크플로우 연결 방식이 사용 경험에 더 큰 영향을 준다는 걸 확인했다.

영상을 따라 만든 뒤에도 끝나지 않았다. 노트, 검색, 실행 환경을 실제로 연결해보면서 모델 자체보다 어떤 지점에 붙이느냐가 더 중요하다는 걸 배웠다.

다음으로 더 살펴보고 싶은 주제들

NEXT 01 · RAG
Vault 전체를 벡터 DB로
노트 검색을 키워드가 아닌 의미 기반 retrieval로. 질문에 가장 관련 있는 노트를 자동 컨텍스트로 주입하는 RAG 파이프라인 구축.
한국어 노트에 잘 맞는 임베딩 모델은 뭘까? bge-m3 vs Qwen-embedding 비교 해보고 싶다.
NEXT 02 · MULTI-AGENT
역할 분담형 에이전트
단일 모델이 아닌 분석가·리뷰어·실행자로 역할 분리. LangGraph / CrewAI 같은 프레임워크 vs 직접 구현, 어느 쪽이 통제하기 좋은지.
에이전트 간 메시지 패싱과 상태 관리는 어떻게 깔끔하게 풀까?
NEXT 03 · QUANTIZATION
양자화 · 추론 최적화
GGUF, AWQ, 4-bit/8-bit 비교. 동일 모델이라도 양자화 방식에 따라 속도·메모리·품질 trade-off가 달라지는 지점을 직접 측정하고 싶다.
CPU-only 추론에서 어디까지 실용적 응답 시간을 뽑아낼 수 있을까?
NEXT 04 · FINE-TUNING
도메인 특화 LoRA
LoRA로 특정 분야(제조 데이터 분석·한국어 기술문서)에 미세조정. 베이스 모델 선택부터 데이터셋 구성, 평가 지표까지 한 사이클 돌려보고 싶다.
소량 데이터로도 의미 있는 도메인 적응이 어디까지 가능한가?
