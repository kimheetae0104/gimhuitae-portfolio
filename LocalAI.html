로컬 모델의 현실

장점보다 먼저
한계를 확인했다

01
긴 컨텍스트의 약점
2000 토큰이 넘는 노트를 그대로 넣으면 응답 품질이 급격히 떨어졌다. "로컬이라서 다 된다"가 아니라, 긴 노트는 결국 청킹과 전처리가 필요하다는 현실을 확인했다.
02
한국어 품질 격차
영어보다 한국어 응답 품질이 눈에 띄게 약했다. 그래서 모델 선택에서도 "가볍게 잘 도는가"만이 아니라 "내 언어에서 실제로 쓸 만한가"를 같이 봐야 한다고 느꼈다.
03
그래도 얻은 것 — 실용적 실험 정신
완벽한 대체재를 만든 건 아니지만, 어디까지는 로컬만으로 충분하고 어디부터는 타협이 필요한지 몸으로 익혔다. 클라우드 의존 없이 AI 도구를 조립하는 감각을 얻었다.
04
작은 모델, 명확한 태스크
범용 질문보다 "이 노트의 요점을 3줄로 정리해줘" 같은 명확한 태스크에서 Gemma 4 모델도 충분히 유용하다. 모델 크기보다 태스크 설계가 더 중요.

품질 보증

숫자보다 어려운 건
맥락 오류를 거르는 일이었다

01
형식 검증
제목·소제목·섹션 구조가 정의된 스키마에 맞는지 확인. JSON 파싱 실패 시 자동 재생성 트리거
02
팩트 검증
생성된 수치(주가·거래량·재무수치)를 수집된 원본 데이터와 대조. 불일치 발견 시 해당 문장 플래그
03
모순 검증
글 내부에서 서로 상충하는 진술 탐지. "실적 개선"과 "매출 감소"가 동시에 언급되면 경고
04
자동 교정
LLM 재시도로도 해결되지 않는 케이스를 결정론적 후처리로 강제 교정. 확률적 모델의 한계를 규칙 기반으로 보완
05
Gemini 검증
Gemini로 종목혼동·수치환각·밸류에이션모순을 다각도 검토. 심각도 판단에 따라 배포 차단 + 알림
5단계

한 번에 잘 쓰는 모델을 찾기보다, 틀린 글은 통과하지 못하게 막는 구조를 먼저 세웠다. Gemini 검증이 critical이면 자동 배포를 멈추고, 최종 통과 글만 배포했다. 그 결과 수치 환각 0건까지 갔다.

Blog Agent Iteration

정답보다 먼저
실패 이유를 확인했다

v1~3
기본 파이프라인 구축
DART API 연결과 단순 프롬프트로 시작했다. 처음엔 "일단 글이 나오게 하자"였지만, 구조화 없이 자유 형식으로 두니 글마다 품질 편차가 너무 컸다.
v4~6
벡터 검색 시도 + 한계 발견
벡터 검색을 먼저 붙였지만, DART 사업보고서처럼 표와 항목 구조가 강한 문서에는 정규식이 더 정확했다. "RAG가 항상 정답은 아니다"라는 걸 여기서 배웠다.
v7~9
검증 레이어 추가
글을 더 잘 쓰게 만드는 것보다, 틀린 글을 걸러내는 쪽이 더 급했다. 형식·팩트·모순 검증을 붙이고, Selenium 크롤러도 타임아웃에 덜 흔들리도록 손봤다.
v10~12
Self-critique + 반자동화 전환
완전 자동화를 밀어붙이기보다, 사람이 마지막에 판단하는 반자동화가 더 현실적이라고 봤다. Self-critique를 붙여 초안을 다듬고, 검수는 끝까지 남겼다.
v13
RAG + 5중 검증 + 다중 배포
ChromaDB에 220개 글을 쌓고, 섹터별 유사글을 참고 자료로 주입했다. 여기에 Gemini 검증까지 얹어 "생성 → 검증 → 배포" 루프를 닫았고, 수치 환각 0건까지 확인했다.

반자동화를 선택한 이유

완전 자동화보다
신뢰 가능한 흐름이 중요했다

01
완전 자동화의 실패
v8에서 완전 자동화를 시도했지만, 검증을 다 통과해도 미묘한 뉘앙스 오류가 남았다. 숫자는 맞지만 맥락이 어긋난 글은 끝까지 사람이 봐야 한다고 결론 내렸다.
02
반복 개선이 실력이다
v1과 v13은 코드 구조가 완전히 다르다. 매 버전의 출력 결과를 보고 다음 문제를 다시 정의하는 식으로 움직였다. 완성보다 개선이 중요한 프로젝트라는 걸 가장 강하게 느꼈다.
03
데이터 파이프라인이 LLM보다 중요하다
프롬프트를 다듬는 것보다, 어떤 소스는 API로 받고 어떤 소스는 정규식으로 뽑을지 정하는 쪽이 훨씬 중요했다. LLM은 파이프라인의 중심이 아니라 한 컴포넌트라는 걸 분명히 봤다.
