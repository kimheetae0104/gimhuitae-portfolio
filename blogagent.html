핵심 기술 01

RAG 역할 분리

구조화 문서(DART 사업보고서 등)의 사실·수치는 API·정규식으로 추출하고, RAG는 직접 발행한 220개 글의 톤·구성 참고에만 사용했다. 벡터 유사도 검색의 약점이 명확한 영역과 강점이 명확한 영역을 분리한 설계.

핵심 기술 02

Gemini · Claude 다단 검증

로컬 LLM(exaone3.5) 초안을 Gemini 2.5 flash-lite로 5기준 자동 평가(종목혼동·수치환각30%+·종목코드·사실창작·밸류에이션모순)하고, 429 시 4단 폴백 큐 + Claude 보조. critical=True면 배포 차단.

왜 로컬을 선택했나

비용 · 의존성 · 보안 제약

클라우드 LLM 운영 시 세 가지 제약이 있었다. ① 호출량 비례 토큰 과금 누적, ② 외부 API 장애·정책 변경 시 파이프라인 중단, ③ 개인 노트·투자 메모의 외부 서버 전송. 로컬 LLM이 이 셋을 동시에 해소할 수 있는지를 실제 도구 2종으로 검증했다.

비용

종량 과금 제거

호출량에 비례하는 토큰 단위 과금이 누적되는 구조 회피. 로컬 모델은 초기 다운로드 외 추가 비용 없음.

의존성

외부 API 격리

핵심 추론을 온디바이스로 분리해 외부 API 장애·정책 변경이 파이프라인 전체를 중단시키지 않는 구조.

보안

외부 전송 차단

개인 노트·투자 메모 등 민감 데이터를 외부 서버로 전송하지 않고 LLM 응답을 받는 경로를 확보.

도구 1 · Obsidian 로컬 AI 작업 환경

컨텍스트 주입 경로가 응답 정확도를 좌우

Obsidian의 현재 활성 노트를 AntiGravity 플러그인이 프롬프트에 자동 주입하고, Ollama가 Gemma 4를 로컬에서 실행해 응답을 같은 노트에 삽입한다. 별도 복붙 없이 현재 작업 컨텍스트 위에서 응답이 생성된다. 동일 질문이라도 작업 컨텍스트가 함께 주입될 때 응답 정확도가 측정 가능하게 향상됐다.

2.1s 평균 응답 (M2 Air) $0 운용 비용 100% 오프라인

도구 2 · 상한가 분석 블로그 자동화 — 오케스트레이션

자율 에이전트 대신 결정론적 오케스트레이션

매일 정해진 시각에 cron이 파이프라인을 트리거한다. 6개 소스(DART·Naver 금융·Google News 등) 병렬 크롤링 → 이슈 점수 산정으로 종목 선정(최대 3개) → RAG로 과거 220개 글 중 섹터 일치 2개 주입 → Ollama exaone3.5(7.8B) 초안 → 7단 검증(형식·팩트·구조모순 13룰·자동교정·Gemini 5기준 평가·Claude 보조) → 통과 글만 발행. LLM이 다음 단계를 판단하는 비결정적 라우팅 대신, 단계와 게이트가 고정된 결정론적 파이프라인으로 설계해 재현성과 디버깅 가능성을 확보했다.

믿을 수 있는 자동화 설계

자동 생성을 믿으려면 모델이 아니라 검증 설계

투자 글에서 틀린 수치 하나는 치명적이다. 그래서 "한 번에 잘 쓰는 모델"을 찾는 대신, 검색 전략과 검증 구조에 시간을 썼다. 두 가지가 핵심이었다.

발견 · v4~6

RAG는 톤·구성 참고에 한정 — 사실 검증은 API·정규식

초기에는 사실 검색까지 벡터 유사도로 처리하려 했다. 그러나 DART 사업보고서처럼 표·항목 구조가 고정된 문서에서는 정규식·API 기반 구조 추출이 의미 유사도 검색보다 정확도가 높았다. 따라서 역할을 분리했다 — 수치·항목 등 사실은 API·정규식으로 추출하고, RAG는 직접 발행한 220개 글의 톤·구성 참고에만 한정했다. 벡터 검색의 약점이 명확한 영역과 강점이 명확한 영역을 각각 다른 도구에 할당한 설계.

사실 · 수치 → API·정규식 ✓

DART 표·항목처럼 구조가 고정된 곳에서 수치를 정확히 집어낸다.

톤 · 구성 → RAG ✓

직접 발행한 220개 글을 참고해 새 글의 톤·구성을 일관되게 유지한다. 각 도구의 강점 영역에 한정.

05

Gemini 2.5 flash-lite 5기준 자동 평가 + Claude 보조, critical=True 시 배포 차단
5단계

고성능 단일 모델을 탐색하는 대신 틀린 글이 통과하지 못하는 구조를 먼저 설계했다. Gemini·Claude 검증이 critical 판정을 내리면 자동 배포가 중단된다. 수치 환각 대부분을 배포 전 단계에서 차단하지만 0%까지는 도달하지 못해, 검증 룰셋은 지속 보강 중이다.

과정 · v1 → v13

정답 도출 전 실패 원인을 먼저 식별

v1~3
기본 파이프라인
DART API 연결과 단순 프롬프트 구성. 구조화 부재로 글마다 품질 편차가 컸다.
v4~6
벡터 검색 시도 → 한계 식별
구조 고정 문서에는 정규식이 더 정확. RAG가 모든 상황의 정답이 아님을 측정으로 확인.
v7~9
검증 레이어 추가
생성 품질 향상보다 오류 차단이 우선. 형식·팩트·모순 검증 단계를 추가.
v10~12
반자동화로 전환
완전 자동화 대신 최종 판단을 사람이 수행하는 반자동 구조 채택. 검수 단계는 자동화 범위에서 제외.
v13
RAG + 7단 검증 + 다채널 배포
ChromaDB에 직접 발행한 220개 글을 색인해 톤 참고에 사용. Gemini·Claude 다단 검증을 추가해 "수집→생성→검증→배포" 루프를 완성. 수치 환각을 배포 전 단계에서 차단하는 구조 확보.

로컬 모델의 한계

로컬 LLM의 한계 — 측정 후 분리

로컬 모델로 모든 작업을 처리할 수는 없었다. 어디까지 로컬로 충분하고 어디부터 클라우드가 필요한지를 측정해, '로컬 초안 + 클라우드 검증' 분리 설계로 수렴했다.

한계 01

긴 컨텍스트 처리 저하

2,000 토큰을 초과하는 입력에서 응답 품질이 급격히 저하됐다. 긴 문서는 청킹·전처리 단계가 필수.

한계 02

한국어 응답 품질 격차

동일 입력에서 영어 대비 한국어 응답 품질이 낮음. 모델 선택 기준에 "사용 언어에서의 출력 품질"을 명시 항목으로 포함.

결과

역할 분리 설계로 수렴

로컬: 초안 생성 + 민감 데이터 처리. 클라우드: 검증 + 고난도 평가. 완전 대체가 아닌 영역별 적합 도구 할당.
