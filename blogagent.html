Blog Agent

개인 데이터를 외부로 보내지 않고, 검증까지 자동으로 도는 블로그 파이프라인을 직접 만들었다.

Ollama 위에 exaone3.5 7.8B로 초안을 쓰고, Gemini로 검증한 뒤 Claude가 최종 글을 다듬어 업로드.

핵심 기술 01

RAG 역할 분리

사실·수치는 DART API와 정규식으로, 톤·구성은 직접 발행한 220개 글을 RAG로 참고한다. 벡터 검색이 약한 곳과 강한 곳을 다른 도구로 나눠 처리했다.

핵심 기술 02

Gemini 검증 → Claude 최종 작성

로컬 초안(exaone3.5)을 Gemini 2.5 flash-lite가 다섯 가지(종목 혼동, 수치 환각 30%+, 종목코드, 사실 창작, 밸류에이션 모순)로 평가. 통과한 초안은 Claude API가 다듬어 업로드. 429 시 4단 폴백 큐 우회, critical이면 배포 차단.

왜 로컬을 선택했나

비용과 의존성, 보안이 걸렸다

클라우드 LLM을 구독해 쓰면서 세 가지가 걸렸다. 로컬 LLM으로 이 셋을 한 번에 풀 수 있는지를 직접 만든 도구 두 개로 확인해 봤다.

01 · 비용

구독 한도 안에서 토큰 관리

Claude 구독은 5시간 단위 한도와 토큰 한도가 있다. 모든 작업을 Claude에 맡기면 금방 한도가 찬다. 그래서 토큰을 많이 쓰는 초안 작성은 로컬 LLM이 처리하고, 정말 중요한 최종 다듬기만 Claude에 맡기는 구조로 나눴다.

02 · 의존성

외부 API와 분리

핵심 추론을 내 머신에서 돌리니, 외부 API가 멈추거나 정책이 바뀌어도 파이프라인 전체가 멈추지 않는다.

03 · 보안

외부 전송 차단

개인 노트나 투자 메모처럼 민감한 데이터를 밖으로 보내지 않고도 LLM 응답을 받게 만들었다.

도구 1 · Obsidian 로컬 AI 작업 환경

모델보다 컨텍스트 주입 경로가 더 중요했다

AntiGravity 플러그인이 지금 열려있는 Obsidian 노트를 프롬프트에 자동으로 넣어준다. Ollama가 Gemma 4를 로컬에서 돌려 답을 그 노트에 바로 써준다.

복붙할 필요 없이 지금 작업 중인 맥락 그대로 답이 나온다. 같은 질문이라도 작업 맥락이 함께 들어가면 응답이 분명히 좋아졌다.

도구 2 · 상한가 분석 블로그 자동화 · 오케스트레이션

LLM이 다음 단계를 정하지 않는 고정 파이프라인

LangChain Agents 같은 자율 에이전트 패턴(LLM이 다음 도구·행동을 스스로 결정)은 디버깅이 어렵고 비결정적이다. 그래서 단계와 검증 게이트를 코드 레벨에서 고정해 뒀다.

로컬 LLM(exaone3.5)이 초안을 쓰고, Gemini가 검증한다. 통과한 글은 Claude가 최종 글로 다듬어 업로드한다. 매번 같은 순서로 돌고, 어디서 멈췄는지 단계별로 추적할 수 있다.

한 글당 4~6분에 끝난다 (직접 쓸 땐 2시간 걸리던 작업) 재시도는 최대 2회까지, critical 판정 나면 그 글은 발행하지 않는다
기술 스택 v13 운영 중
그룹구성핵심 결정
모델과 추론 cron · Ollama exaone3.5 7.8B cron이 매일 정시에 깨우고 로컬 LLM이 초안을 쓴다. 기본은 로컬 모드라 API 비용이 들지 않고 데이터도 밖으로 나가지 않는다.
RAG와 데이터 nomic-embed-text 768d · ChromaDB · DART, 네이버 금융, Google News RSS 6소스 직접 발행한 220개 글을 벡터로 만들어 ChromaDB에 넣어뒀다. 섹터 필터로 한 번 좁히고 가장 가까운 글 2개만 가져다 쓴다. 뉴스는 18개 언론사만 화이트리스트로 받아 본문 노이즈를 줄였다.
검증 단계 형식 → 팩트(DART 50%+ 차이) → 구조 모순 13룰 → 자동 교정 → Gemini 5가지 기준 → 4단 폴백 큐 critical 판정이 나오면 배포가 멈춘다. 재시도는 최대 2번. Gemini 무료 한도(분당 15회, 하루 100만 토큰)는 폴백 큐로 우회한다. 모든 단계가 점수와 이슈를 객체로 남긴다.
최종 작성과 배포 Claude API, 네이버 블로그(Selenium), Google Sheets, Obsidian, Telegram 검증 통과한 초안을 Claude가 최종 글로 다듬는다. undetected-chromedriver로 네이버 블로그에 자동 로그인해 업로드하고, gspread 서비스 계정으로 시트에도 기록한다. critical 알림에는 검증 점수가 따라온다.

믿을 수 있는 자동화 설계

자동 생성을 믿으려면 모델보다 검증을 만들어야 했다

투자 글에서 틀린 수치 하나는 치명적이다. 그래서 "한 번에 잘 쓰는 모델"을 찾기보다, 검색 전략과 검증 구조에 시간을 더 썼다. 두 가지가 핵심이었다.

발견 · v4~6

RAG는 톤만, 사실 검증은 API와 정규식

처음에는 사실 검색까지 벡터 유사도로 처리하려 했다. 그런데 DART 사업보고서처럼 표와 항목 구조가 고정된 문서에서는 정규식과 API로 직접 뽑는 게 의미 유사도 검색보다 정확했다.

그래서 역할을 갈랐다. 수치와 항목 같은 사실은 API와 정규식으로 뽑고, RAG는 직접 발행한 220개 글의 톤과 구성을 참고할 때만 썼다. 벡터 검색이 약한 곳과 강한 곳을 다른 도구로 처리한 셈이다.

방어 · 5중 검증

틀린 글은 통과 차단

01
형식
스키마가 맞지 않으면 자동으로 다시 쓰게 한다.
02
팩트
생성된 수치를 원본 데이터와 대조해서 안 맞으면 표시한다.
03
모순
"실적 개선"과 "매출 감소"가 같이 나오는 경우 같은 모순을 찾아낸다.
04
자동 교정
LLM 재시도로도 안 되는 부분은 규칙 기반 후처리로 강제로 고친다.
05
최종 검증
Gemini 2.5 flash-lite가 5가지 기준으로 평가한다. 통과한 글만 Claude가 다듬어 발행하고, critical 판정이면 배포가 멈춘다.
5단계

좋은 모델 하나를 찾기보다 틀린 글이 통과하지 못하는 구조를 먼저 만들었다. Gemini 검증이 critical을 잡으면 배포가 멈추고, 통과한 글만 Claude가 최종 다듬어 발행된다. 환각 0%까지는 못 가서 검증 룰은 지금도 계속 다듬는 중이다.

과정 · v1 → v13

왜 이렇게 됐는지 — 13번의 시도

v1~6
한 번에 잘 쓰는 모델 찾기 시도
큰 모델을 쓰면 환각이 줄어들 거라 생각해 모델만 바꿔봤다. 같은 입력이면 모델을 바꿔도 환각 패턴이 비슷하게 반복됐다. 모델보다 입력에 사실이 충분히 들어가야 한다는 걸 여기서 확인했다.
v7~12
완전 자동화 시도 후 반자동으로 후퇴
검증 단계를 붙여 자동 발행까지 가봤지만, 검수 없이 그대로 올리기엔 위험이 컸다. 결국 마지막 판단은 내가 직접 하는 반자동 구조로 바꿨다.
v13
지금 운영 중인 구조
초안은 로컬, 검증은 Gemini, 최종 작성은 Claude로 역할을 나눴다. 수치 환각을 배포 전 단계에서 잡을 수 있게 됐다.

로컬 모델의 한계

왜 로컬로 다 되지 않았는지

단순히 "로컬 모델은 약하다"가 아니라, 어떤 조건에서 막혔는지를 직접 돌려보며 확인했다. 한계는 모델 자체보다 장비 사양과 환경 셋팅에서 나왔다.

한계 01

장비 사양에 묶인 모델 크기

통합 메모리 24GB 노트북에서는 7~8B급이 한계였다. 한국어가 잘 되는 더 큰 모델(70B 이상)을 안정적으로 돌리려면 별도 GPU 서버가 필요하다. 모델 크기를 못 올리니 긴 컨텍스트(2,000 토큰 이상)에서도 응답 품질이 빨리 떨어졌다.

한계 02

환경 셋팅에 들어가는 비용

Ollama 설치, 모델 다운로드, 메모리 관리, 모델 교체할 때마다 셋팅을 다시 잡는 작업이 누적된다. 한국어 품질이 좋은 큰 모델로 갈수록 이 비용이 커져서, 7B급에서 멈출 수밖에 없었다.

결론

역할을 갈라서 썼다

7B급 로컬은 초안과 컨텍스트 주입에 한정하고, 한국어 품질이 결정적인 최종 작성은 Claude로 다듬게 했다. 한쪽이 다른 한쪽을 대체하기보다 각자 잘하는 일을 분담시켰다.
