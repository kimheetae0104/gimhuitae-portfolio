핵심 기술 01

향미 페어링 추천 알고리즘

두 재료의 향미 호환성을 자체 레시피 코퍼스의 공동 출현 빈도(PMI 기반)로 계산했다. 자체 레시피 4,976개 페어링 데이터를 활용해 비슷한 향미 특성끼리 군집을 만든 뒤, 그 안에서 재료를 추천한다.

출발점

냉장고 안에 들어간 재료,
잊혀진 채 썩기 마련

야채 칸 뒤편이나 비닐봉지 속의 재료는 문을 닫는 순간 시야에서 사라진다.
다시 발견했을 때는 이미 시들어 있어, 그대로 음식물 쓰레기가 됐다.

환경부·한국환경공단 통계에 따르면, 국내 음식물 쓰레기의 약 70%가 가정과 소형 음식점에서 발생하며, 처리에만 연간 6,000억 원 이상이 투입된다.

남은 재료로 무엇을 만들 수 있는지 먼저 알려주면 버리는 양이 줄어들 거라 보았다.
그래서 남은 재료로 만들 수 있는 레시피를 추천하는 앱을 만들기로 했다.

출처: 환경부·한국환경공단 「2022년도 쓰레기 종량제 현황」 (2023)

왜 향미 페어링인가

재료를 찾는 앱은 많다.
맛의 조합을 찾는 앱은 없었다.

대부분의 레시피 앱은 재료 이름·인기·태그로 추천한다.
정작 왜 이 재료들이 어울리는지는 설명하지 못한다.
그 "이유 없는 추천"이 늘 아쉬웠다.

음식의 향미에는 패턴이 있다.
실제 셰프의 레시피에서 자주 함께 등장하는 재료 조합은
대체로 더 자연스럽게 어울린다.
그렇다면 추천도 그 패턴 위에 세울 수 있다고 봤다.

자체 알고리즘 · PMI Co-occurrence
자체 레시피 코퍼스 기반 향미 페어링
USDA MyPlate (Public Domain) · 식품의약품안전처 COOKRCP01 (공공누리 1유형) · JANN AI 큐레이션
JANN의 추천 모델은 2,544개 공개 라이선스 레시피 코퍼스에서 재료 공동 출현 패턴을 PMI(Pointwise Mutual Information) 기반으로 분석해 4,976개 향미 페어링 점수를 구축했다. 모든 데이터셋은 상업 사용 가능한 라이선스로 정리되어 있다.

추천의 근거

유사도는 PMI로 계산

인기순이 아니라, 두 재료가 실제 레시피에서 얼마나 함께 등장하는지로 본다.

t-SNE — 재료 이름이 아니라 향미 프로필로 차원을 줄이면, 비슷한 맛끼리 모인다.

두 재료의 향미 호환성은 공동 출현 빈도 ÷ 출현 곱(PMI Co-occurrence)으로 정했다.
레시피 코퍼스 내 공동 출현 패턴을 보는 것이다.

원본 DB가 서양 식재료 중심이라, 김치·된장·고추장 같은 한국 재료에
한-영 매핑을 직접 더해 로컬라이징했다.

데이터 · 도메인 일치

모델보다 데이터가 먼저였다

독립 식재료 사진으로 학습한 모델이 냉장고 환경에서 Recall 24%로 떨어진 것을 보고, 모델 구조를 바꾸기 전에 실제 사용 환경 데이터로 다시 학습.

  • 가설 검증 · 학습 도메인과 실제 사용 환경이 다르면 같은 모델이라도 성능이 무너진다는 것을 수치로 직접 확인
  • 의사결정 · 더 큰 모델로 가지 않고, 실제 냉장고 내부 사진 데이터셋으로 다시 학습해 실사용 수준으로 회복
학습 최적화 · 1 epoch 161분 → 17분

병목의 진짜 원인을 짚어 약 90% 단축

Mac에서 1 epoch에 161분 → 17분으로 단축. 핵심은 GPU 성능 탓을 멈추고 병목의 진짜 위치를 짚은 것.

  • 원인 진단 · 처음엔 GPU 한계로 의심했지만, 로그·메모리 사용량을 보고 프레임워크의 처리 경로 버그와 메모리 스왑이 진짜 원인임을 특정
  • 해결 접근 · 하드웨어 교체 없이, 문제 구간을 우회하도록 학습 파이프라인을 조정해 동일 장비에서 그대로 학습
  • 품질 확인 · 빨라진 만큼 안정성도 함께 봐야 해서, 학습 로스와 과적합 지표를 병행 모니터링
MLOps · 학습 → 앱 배포

1인 개발에서도 실험 사이클을 짧게 가져가기 위한 자동화

학습이 끝나는 시점부터 iOS 앱에 모델이 올라가기까지의 모든 수작업을 자동화. 반복 실험을 빠르게 돌리기 위한 인프라 결정.

  • 자동화 범위 · 학습 완료 감지 → 모델 변환 → 앱 리소스 교체 → 클래스 목록 코드 동기화까지 한 흐름
  • 환경 분리 · 무거운 학습은 클라우드 GPU에서, 변환·배포는 로컬 Mac에서 — 비용과 빌드 사이클을 분리
  • 결과 · 최종 33개 식재료 클래스 · 5.2MB 모델, 네트워크 없이 온디바이스 실시간 추론 가능
에지 케이스 · LLM 인식 오류

한 군데 패치로 끝나지 않는 문제, 다중 방어로 접근

GPT-4o Vision이 흰 용기를 두부로 오인하는 케이스. 한 지점만 손대면 다른 케이스로 새는 구조라 모델·프롬프트·결과 필터 세 지점에서 동시에 보강.

  • 방어 전략 · 한 지점이 뚫려도 다음 단계에서 걸러지도록 인식·생성·검증을 분리 설계
  • 한계 인정 · LLM 인식 오류는 본질적 제약이라 완전 제거 대신 케이스 누적으로 점진 개선
  • 운영 관점 · 단발성 버그가 아니라 운영 중 학습 데이터·필터를 지속 갱신해야 하는 문제로 정의
